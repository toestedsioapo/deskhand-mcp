# 0010 — The drafted body lives in `plan_json`, and only until the action ends

Status: Accepted (owner-approved decisions, 2026-11-17, M4a plan decision 2, with the owner's ruling on the hash)

**Context.** `inbox_draft_reply` plans a Gmail draft. The human who approves it must read the whole body, and `action_apply` must write exactly that body. Both need the text to be stored somewhere between plan and apply. CLAUDE.md says Deskhand never stores full email bodies, so this is the one exception, and it needs limits: where the text is kept, who can see it, how the hash covers it, and when it is removed.

**Decision.**

1. **Where.** The body is stored only in `actions.plan_json`, under `draft.body`. `deskhand pending` and `deskhand approve` show it in full. Everywhere else it appears as `[omitted N chars sha256:<8 hex>]`, the M2a redaction marker produced by the same function (`omittedMarker`): `actions.input_json` (the tool input key is `body`, already a body key), every `events.preview_json`, `ledger_query`, `action_explain` (`plan` and `diff`), the `inbox_draft_reply` result, the `action_apply` result, and `result_json`, which stores ids and `bodySha256`, never the text. The fixture `write_log` line goes through `redactPreview` too.
2. **The hash covers the body through `bodySha256`, not the text (owner ruling, 2026-11-17).** `plan_hash` is the SHA-256 of the canonical JSON of the plan with `draft.body` and `draft.bodyRemoved` deleted. The function is `hashablePlan(plan)` in `src/ledger/canonical.ts`, and `planHash` calls it. It is a no-op for every other plan kind, so calendar hashes do not change. The plan schema requires that a present `body` matches `bodyChars` and `bodySha256`. Removing the body therefore never changes `plan_hash`, and an edited body is still caught: `deskhand pending` shows `(invalid plan)`, `deskhand approve` refuses with `PLAN_MODIFIED`, and apply gives `PLAN_MODIFIED` (status `failed`). `plan_json` must still equal `canonicalJson(plan)` byte for byte, body included. There is no exception for approved plans: the same rule holds at every status.
3. **How long.** The body is removed from `plan_json` as soon as the action can no longer be written. The row is rewritten with `body` deleted and `bodyRemoved: true`, keeping `bodyChars` and the full `bodySha256`. That applies to `applied` (the text now lives in the Gmail draft), `rejected`, `failed`, and `planned` or `approved` with `now >= expires_at` (an unparseable `expires_at` counts as expired). An approved plan past expiry can no longer write (gate 7). Recovery (gate 6) still finds a draft that a crashed apply left behind, because `matches` compares the draft's body hash with `bodySha256`, which survives the sweep. An unexpired `approved` plan keeps its body, because it can still be applied. A sweep (`sweepDraftBodies`) runs at server start, after every `action_apply`, after `deskhand reject`, and at the start of `deskhand pending` and of `createPlan`. The longest a body stays in the ledger is the plan TTL (default 24 hours, at most 7 days) plus the time until Deskhand next runs.
4. **A plan without its body never writes.** `deskhand approve` refuses a `bodyRemoved` plan: `PLAN_EXPIRED` when it is expired (expiry is checked first), else `PLAN_MODIFIED` (an unexpired plan can only lose its body through tampering). Apply on a `bodyRemoved` approved plan runs recovery (gate 6) and expiry (gate 7) as usual. If it gets past both, it fails `PLAN_MODIFIED` before the re-check (gate 8), and the provider is never asked to write.
5. **Disk.** `src/ledger/db.ts` sets `PRAGMA secure_delete = ON`, so SQLite zeroes the pages it overwrites. Every sweep, even one that changed no rows, then runs `PRAGMA wal_checkpoint(TRUNCATE)` with `busy_timeout` 0, so it never waits on another connection. The removed text leaves the WAL in that sweep when no other connection is reading, otherwise at the next sweep whose checkpoint succeeds, or when the last connection closes cleanly. Backups and copies of `ledger.db` made earlier still hold the text. SECURITY.md says so.
6. **The agent's reason follows the body (owner decision, 2026-11-23).** `rationale` can quote mail, so a draft plan treats it like the body: `plan_hash` covers it through `rationaleSha256`, the approver sees it as one `agent's reason:` line, the agent sees it only as untrusted text, and the sweep removes it.

**Rejected alternatives.** Not storing the body and asking the agent to resend it at apply (the human would approve text that Deskhand cannot show again, and a different body could be written). Hashing the full body text inside `plan_hash` (removing the body would then change the hash, so the sweep would have to keep a second hash and the apply-time checks would grow a special case). Keeping the body of an approved plan until it is applied, past expiry (it can no longer write, so the text has no use). Encrypting the body in `plan_json` (the key would sit next to the file, and the human still needs the plain text).

**Consequences.** `plan_json` can hold mailbox-derived text the agent wrote, for a bounded time. The ledger contract (`docs/ledger-contract.md`, "Plan shape: `mail.create_draft_reply`") documents the exception, the sweep and `bodyRemoved`. No table, column or value set changes, so the ledger stays at schema v3. The plan-kind interface gets two optional generic hooks (a body-integrity check before the schema parse, and a "can still write" check before gate 8), so `apply.ts` and `approve.ts` stay free of mail logic.
