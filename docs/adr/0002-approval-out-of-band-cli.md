# 0002 — Out-of-band approval, plan-hash binding, apply-time re-check

Status: Accepted (owner review, 2026-11-09)

**Context.** The agent drives MCP tools, so any approval path reachable through a tool can be driven by a prompt-injected agent.

**Decision.**
1. **Approval is a CLI action, not an MCP tool.** `action_apply` only reads approvals from the ledger. `deskhand approve <id>` requires an interactive TTY on both stdin and stdout, prints the human-readable diff and the first 8 hex chars of the plan hash, and requires the user to type the **last 4 characters of the action_id**. No `--yes`, no piped input. The ledger records `approved_by` and `approval_method` (`cli_tty`). `deskhand reject <id> [reason]` needs no TTY (worst case an agent rejects a good plan, which is safe) but records `rejection_method` (`cli_tty` or `cli_no_tty`).
2. **Approve refuses, and leaves status unchanged, when** the plan is expired, already approved (`ALREADY_APPROVED`) or otherwise not `planned` (`NOT_PENDING`: rejected, failed, applied), the recomputed hash differs from `plan_hash`, the typed last 4 are wrong, or there is no TTY. Every refusal writes an `events` row (`approve_refused`, with an `error_code`); the `actions` row is not touched.
3. **Hash binding.** At plan time store `plan_hash = sha256(canonical_json(plan_json))`. Approve recomputes from stored `plan_json`, verifies it equals `plan_hash`, and records `approved_plan_hash`. `action_apply` recomputes again and refuses (status `failed`, code `PLAN_MODIFIED`) unless all three match. The apply gate order is: writes flag, exists, applied-replay, approved, hash (`PLAN_MODIFIED`), recovery, expiry, re-check, write; `docs/ledger-contract.md` is the authority. `plan_json` is never updated after planning. Anything that changes what the plan does to the outside world is part of `plan_json` and therefore of the hash, including whether attendees would be notified (`sendUpdates`, default `none`).
4. **Apply-time re-check.** Before a calendar write, confirm the slot is still free and referenced events are unchanged (etag/updated). Otherwise fail with `STALE_PLAN`, log it, and do not write. Failed is terminal; the agent re-plans.
5. **Idempotency.** Provider writes use an idempotency key derived from `action_id` (e.g. a deterministic Calendar event id), so a crash between the provider write and the ledger update can't double-apply.
6. **`ApprovalSource` seam.** The CLI is the only v1 implementation; MCP elicitation (B) or Deskflow approval (P4) can be added later by recording a different `approval_method`, without changing apply.
7. **Action-id collisions.** The last 4 characters are the confirmation, so they must tell pending plans apart. At plan time, if the new id's last 4 characters equal the last 4 of any pending (`planned` or `approved`-but-unapplied) action, regenerate the id until they differ. As a defensive check, `approve` still refuses if two pending ids share the same last 4 (`ID_COLLISION`). Both paths are tested.
8. **Invocation and deny rules.** The canonical way to run the CLI when only the `npx` install exists is `npx -p @marvinliem/deskhand-mcp deskhand approve <id>`. The README ships Claude Code deny rules covering `deskhand`, `npx`, `pnpm exec` and `node dist/cli.js` variants (SECURITY.md has the list). They are best-effort: Claude Code matches the command text, not the program.

**Consequences / honest limits.** The TTY rule is a speed bump, not a security boundary: an agent with shell access could allocate a pty and type the confirmation. The hash protects against bugs and in-flight modification, not an attacker who can already write the SQLite file as the same user (they can edit all three values). Documented in SECURITY.md. Mitigation if needed later: HMAC with a key outside the DB.

**Rejected.** Approval via an MCP tool (self-approvable); elicitation as v1 (client-controlled, uneven support).
