# M4b Gmail Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the M4a inbox tools against the owner's real Gmail with `gmail.readonly` at login and `gmail.compose` only after `deskhand auth upgrade` with writes enabled. The adapter physically cannot reach a send endpoint.

**Architecture:** A Gmail adapter implements `MailProvider` over the M3b `googleRequest` (built-in `fetch`, no SDK, no redirects). Every Gmail request must match a fixed allowlist of (method, path) before it is sent, so `messages/send`, `drafts/send`, `modify` and `trash` are refused in our code before any network call. MIME parsing and building live in one module. Tests use hand-written recorded responses only.

**Tech Stack:** Node >=24.15 built-ins (`fetch`, `TextDecoder`, `Buffer`), TypeScript strict, Zod 4.6.7, Vitest. No new dependencies.

**Spec:** M4a plan (`docs/superpowers/plans/2026-11-17-m4a-inbox-fixture.md`, decisions 2 to 13), ADR 0007 (and its M4 addendum written in M4a Task 1), ADR 0009, ADR 0010, `docs/SECURITY.md`, `docs/TEST_PLAN.md` ("Scopes", "Drafts only"), `docs/google-oauth-setup.md`.

**Depends on:** M4a merged.

## Decisions (approved by the owner 2026-11-17)

1. **Scopes (owner's rule).**
   - `deskhand auth login` asks for `calendar.readonly` and `gmail.readonly`.
   - `deskhand auth upgrade` (refuses unless `DESKHAND_ALLOW_WRITES=1`) adds `calendar.events` and `gmail.compose`.
   - `gmail.send`, `gmail.modify` and `https://mail.google.com/` are never requested.
   - A token from M3 (calendar scopes only) keeps the calendar tools working; the inbox tools answer `AUTH_REQUIRED` with `Run: deskhand auth login`.
   - Calendar-only use now means granting a restricted Gmail read scope too. This is noted in the setup guide; a calendar-only login flag is not planned.
2. **Endpoint allowlist.** It is checked inside `googleRequest` for the Gmail service, on the parsed URL (path segments percent-decoded once and checked against `^[A-Za-z0-9_-]{1,64}$`):

   | Method | Path |
   |---|---|
   | GET | `/gmail/v1/users/me/profile` |
   | GET | `/gmail/v1/users/me/threads` |
   | GET | `/gmail/v1/users/me/threads/{id}` |
   | GET | `/gmail/v1/users/me/drafts` |
   | GET | `/gmail/v1/users/me/drafts/{id}` |
   | POST | `/gmail/v1/users/me/drafts` |

   Anything else, `/drafts/send` and `/messages/send` included, is a `ProviderError` with phrase `refused request to an endpoint outside the allowlist`, before `fetch` is called. This is the "no send endpoint is ever called" guarantee in code, on top of `MailProvider` having no send method.
3. **Draft lookup:** `GET drafts?q=rfc822msgid:<id without angle brackets>&maxResults=10`, then `GET drafts/{id}?format=full` for each hit, and the result is present only when its `Message-ID` header equals ours exactly. **Second route, for a search index that lags (decision 8):** when search finds nothing, `GET threads/{threadId}?format=metadata&metadataHeaders=Message-ID` looks for a `DRAFT`-labelled message with our exact header. If one exists, page `GET drafts?maxResults=100` (at most 5 pages) to map its message id to a draft id, then `drafts.get`. A draft message that cannot be mapped is a retryable `ProviderError`, so no POST follows. `lookupDraft` therefore takes the thread id: `lookupDraft(messageIdHeader: string, threadId: string)`. **To verify live (Task 4):** that Gmail keeps the client-supplied `Message-ID` and the `Bcc` header on a draft. If it does not, the fallback (recorded now, built only if the live check fails, as a fix before merge) is to look up the thread's `DRAFT`-labelled messages and match recipients, subject and body hash (M4a decision 8). **Result (live check, 2026-11-25): Gmail keeps the Bcc but rewrites the `Message-ID`.** Replaced by the owner's decision of that date (ASSUMPTIONS, "Draft identity after the live check"): the draft id recorded in a `write_landed` row as soon as the POST returns it is the identity, with content matching over `drafts.list` as the fallback before an id is recorded. The search and thread routes above are removed, and no `Message-ID` is sent (decision 4).
4. **Draft MIME** (`buildDraftMime`). The headers, in this order: `In-Reply-To` (when present), `References` (when non-empty), `To`, `Cc` (when non-empty), `Bcc` (when non-empty), `Subject`, `MIME-Version: 1.0`, `Content-Type: text/plain; charset=UTF-8`, `Content-Transfer-Encoding: base64`.
   - Subject: as is when it is printable ASCII, otherwise RFC 2047 `=?UTF-8?B?…?=` encoded words of at most 75 characters, folded with CRLF and a space.
   - Body: `\n` becomes CRLF, then base64 in 76-column lines.
   - The draft is sent as `{ message: { raw: base64url(mime), threadId } }`. No `From` header: Gmail sets the account address.
   - The M4a plan schema already makes CR or LF impossible in any header value. `buildDraftMime` still checks that every header value is free of CR, LF and NUL and throws a `ProviderError` with phrase `invalid header value` (defence in depth).
5. **Reading.**
   - `threads.get?format=full`. Messages are sorted by `internalDate`. Messages labelled `DRAFT`, `TRASH` or `SPAM` are dropped, so our own draft never becomes the "latest message" and never trips the re-check.
   - Body: the first body-bearing leaf in document order, skipping attachments and never entering `message/rfc822`; inside a `multipart/alternative`, the `text/plain` in that subtree wins over `text/html`. A `text/html` body is converted by a small `htmlToText`: drop `script`, `style` and `head`; turn `br`, `p`, `div`, `li` and `tr` into newlines; remove the other tags; decode the named entities `amp lt gt quot apos nbsp` and numeric entities; collapse runs of blank lines.
   - The charset comes from `Content-Type`, through `TextDecoder` (`fatal: false`). An unknown label falls back to UTF-8. Bodies are cut at 20 000 characters.
   - At most 10 MIME levels and 200 parts are read; deeper or more is cut, not an error.
   - Addresses come from a small RFC 5322 list parser: quoted strings, comments, `<…>` and groups. RFC 2047 words in names and subjects are decoded. An entry that does not parse is dropped from the address lists (so it never counts as on the thread).
   - Search: `threads.list?q=<query>&maxResults=<limit>`, then `threads.get?format=metadata&metadataHeaders=From&metadataHeaders=Subject&metadataHeaders=Date` per thread. `truncated` is true when `nextPageToken` is present.
6. **Recordings are hand-written** from the Gmail API reference with made-up ids and `@example.com` addresses (M3b decision 6). The live check proves them, and any mismatch is fixed in the recording and the adapter together before merge.
7. **The re-check compares the thread's whole message set (M4a follow-up 4; added 2026-11-23, pending owner review; amends M4a decision 8).**
   - The plan stores `observed.messageIdsSha256`: the lowercase hex SHA-256 of `JSON.stringify` of the thread's unique non-draft, non-trash, non-spam message ids, sorted by code unit. `plan_hash` covers it.
   - The ids come from a new `MailProvider.threadMessageIds(threadId)`, with no message cap, so a message older than the newest 100 still counts. On Gmail it is `threads.get?format=minimal` (allowlisted path, no bodies or headers fetched).
   - At plan time the ids are read **before** `getThread`. A message that arrives between the two reads is then missing from the stored hash and the plan goes stale, instead of being hashed without the planner having seen it.
   - At apply, after the account check: no thread is `THREAD_GONE`; a different latest id keeps `THREAD_NEW_MESSAGE`; any other difference in the set, including a removed message, is `STALE_PLAN` with the new phrase `the thread's messages changed since planning`. Label or read-state changes do not change the set.
   - The field is optional in the stored schema, so applied M4a plans stay valid history. A plan without it cannot pass the re-check: `STALE_PLAN`, phrase `the plan has no record of the thread's messages`, no write.
8. **Write claim for drafts (M4a follow-up 11; owner rules 2026-11-23).** Gmail has no unique key on `Message-ID`, so the ledger serialises the write. Ledger schema v4 adds the event kind `write_claimed` (outcome `ok`, tool `action_apply`).
   - **Who uses it:** a plan kind with `needsWriteClaim: true`. Only `mail.create_draft_reply` sets it; a calendar write already has a provider-enforced fixed id.
   - **Taking it (gate 8b, after the re-check, before the write):** inside `BEGIN IMMEDIATE`, confirm `status = 'approved'`, read this action's newest `write_claimed` row, and insert a new one only if there is none, it is released, or it is at least `WRITE_CLAIM_HOLD_MS = 60_000` old. Otherwise refuse with `apply_refused` (`PROVIDER_ERROR`), status unchanged, fixed note `another apply of this action is in progress or may still be landing; retry in a minute`, and no POST.
   - **After taking it:** run the draft lookup again and settle a hit as in gate 6. If it is absent, confirm in a new `BEGIN IMMEDIATE` that our claim is still the newest and younger than `WRITE_CLAIM_START_LIMIT_MS = 30_000`, else refuse with the same note and no POST. Then POST once. `createDraft` on Gmail makes no lookup of its own, so nothing unbounded sits between this check and the POST.
   - **Release:** only an exit known to have sent no POST releases the claim: a lookup failure after the claim, the start-limit refusal, or `AuthRequiredError` raised before the request. It is an `apply_refused` row with `preview.output = { releasedClaim: <claim event id> }`. A crash, timeout, network error, `429`, `5xx` or unreadable `2xx` never releases it.
   - **When a retry may POST again:** only after the claim is at least 60 s old **and** a lookup made under the new claim finds nothing. Not immediately after a failed POST, because a `500` can mean the draft landed.
   - **Why 60 s:** the POST starts within 30 s of the claim, a token refresh and the POST are each capped at 10 s by `googleRequest` (the draft POST uses `singleSend`: a `401` refreshes the token but never re-sends, so there is exactly one send), so the holder's request has ended by 50 s. The last 10 s are margin for the write to become readable.
   - **Re-check interplay:** a failed re-check while an unreleased claim is younger than 60 s is the retryable `an earlier write attempt may still be landing; retry later`, never `failed`.
   - **Residual risk (documented in SECURITY.md):** a process suspended for over 60 s between its last check and its POST, or a landed draft that both lookup routes miss after 60 s, can leave a second draft. It is a draft and is never sent.
9. **"Mine" means sent (M4a follow-up 10; owner rule 2026-11-23).** `MailMessage.sentByOwner: boolean` is true only for Gmail's `SENT` label or the fixture's explicit `sent: true` (additive key, `fixture_version` unchanged). `From: <owner>` alone no longer counts in default recipients (amends M4a decision 6).

## Global Constraints

- Every rule from the M4a plan's Global Constraints still holds.
- Scope sets are exactly: read `[calendar.readonly, gmail.readonly]`; write adds `[calendar.events, gmail.compose]`, in that order, only with `DESKHAND_ALLOW_WRITES=1`.
- No Gmail request leaves `googleRequest` unless it is on the decision-2 allowlist. Host stays `www.googleapis.com` and `redirect: "error"` is kept.
- No token, response body, message body or raw MIME appears in a thrown message, `actions.error`, a preview or stderr.
- No live network in tests; `replay-fetch` fails on any `/send` URL.
- Test first. Commits carry no attribution lines.

## Review Focus

1. **A message with no `text/plain` part and malformed HTML** (an unclosed tag, `<script>` with a `>` inside a string). Expected: readable text, no script text, no exception, wrapped as untrusted. Test in Task 2.
2. **A body in `ISO-8859-1` or `windows-1252`, and a part with an unknown charset label.** Expected: decoded correctly, or decoded as UTF-8 with replacement characters, and never thrown. Test in Task 2.
3. **The token predates M4** (calendar scopes only). Expected: calendar tools work; inbox tools answer `AUTH_REQUIRED` `Not signed in to Google. Run: deskhand auth login`; no Gmail request is sent. Test in Task 1.
4. **A thread id in a request path holding `/`, `..`, `%2F` or `?`.** Expected: refused by the allowlist before `fetch`. (The tool's `threadIdSchema` already refuses it; this is the adapter's own guard.) Test in Task 1.
5. **Our draft is the newest message of the thread when apply runs again** (a replay or recovery after the draft was created). Expected: the re-check ignores `DRAFT` messages, so recovery finds the draft and records `applied`, not `STALE_PLAN`. Test in Task 3.
