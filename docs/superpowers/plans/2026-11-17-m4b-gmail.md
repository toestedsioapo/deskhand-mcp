# M4b Gmail Adapter Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the M4a inbox tools against the owner's real Gmail with `gmail.readonly` at login and `gmail.compose` only after `deskhand auth upgrade` with writes enabled. The adapter physically cannot reach a send endpoint.

**Architecture:** A Gmail adapter implements `MailProvider` over the M3b `googleRequest` (built-in `fetch`, no SDK, no redirects). Every Gmail request must match a fixed allowlist of (method, path) before it is sent, so `messages/send`, `drafts/send`, `modify` and `trash` are refused in our code before any network call. MIME parsing and building live in one module. Tests use hand-written recorded responses only.

**Tech Stack:** Node >=24.15 built-ins (`fetch`, `TextDecoder`, `Buffer`), TypeScript strict, Zod 4.6.7, Vitest. No new dependencies.

**Spec:** M4a plan (`docs/superpowers/plans/2026-11-17-m4a-inbox-fixture.md`, decisions 2 to 13), ADR 0007 (and its M4 addendum written in M4a Task 1), ADR 0009, ADR 0010, `docs/SECURITY.md`, `docs/TEST_PLAN.md` ("Scopes", "Drafts only"), `docs/google-oauth-setup.md`.

**Depends on:** M4a merged.

## Decisions (proposed 2026-11-17, for owner review)

1. **Scopes (owner's rule).**
   - `deskhand auth login` asks for `calendar.readonly` and `gmail.readonly`.
   - `deskhand auth upgrade` (refuses unless `DESKHAND_ALLOW_WRITES=1`) adds `calendar.events` and `gmail.compose`.
   - `gmail.send`, `gmail.modify` and `https://mail.google.com/` are never requested.
   - A token from M3 (calendar scopes only) keeps the calendar tools working; the inbox tools answer `AUTH_REQUIRED` with `Run: deskhand auth login`.
   - Calendar-only use now means granting a restricted Gmail read scope too. This is noted in the setup guide; a calendar-only login flag is not planned.
2. **Endpoint allowlist.** It is checked inside `googleRequest` for the Gmail service, on the parsed URL (path segments percent-decoded once and checked against `^[A-Za-z0-9_-]{1,64}$`):

   | Method | Path |
   |---|---|
   | GET | `/gmail/v1/users/me/profile` |
   | GET | `/gmail/v1/users/me/threads` |
   | GET | `/gmail/v1/users/me/threads/{id}` |
   | GET | `/gmail/v1/users/me/drafts` |
   | GET | `/gmail/v1/users/me/drafts/{id}` |
   | POST | `/gmail/v1/users/me/drafts` |

   Anything else, `/drafts/send` and `/messages/send` included, is a `ProviderError` with phrase `refused request to an endpoint outside the allowlist`, before `fetch` is called. This is the "no send endpoint is ever called" guarantee in code, on top of `MailProvider` having no send method.
3. **Draft lookup:** `GET drafts?q=rfc822msgid:<id without angle brackets>&maxResults=10`, then `GET drafts/{id}?format=full` for each hit, and the result is present only when its `Message-ID` header equals ours exactly. **To verify live (Task 4):** that Gmail keeps the client-supplied `Message-ID` and the `Bcc` header on a draft. If it does not, the fallback (recorded now, built only if the live check fails, as a fix before merge) is to look up the thread's `DRAFT`-labelled messages and match recipients, subject and body hash (M4a decision 8).
4. **Draft MIME** (`buildDraftMime`). The headers, in this order: `Message-ID`, `In-Reply-To` (when present), `References` (when non-empty), `To`, `Cc` (when non-empty), `Bcc` (when non-empty), `Subject`, `MIME-Version: 1.0`, `Content-Type: text/plain; charset=UTF-8`, `Content-Transfer-Encoding: base64`.
   - Subject: as is when it is printable ASCII, otherwise RFC 2047 `=?UTF-8?B?…?=` encoded words of at most 75 characters, folded with CRLF and a space.
   - Body: `\n` becomes CRLF, then base64 in 76-column lines.
   - The draft is sent as `{ message: { raw: base64url(mime), threadId } }`. No `From` header: Gmail sets the account address.
   - The M4a plan schema already makes CR or LF impossible in any header value. `buildDraftMime` still checks that every header value is free of CR, LF and NUL and throws a `ProviderError` with phrase `invalid header value` (defence in depth).
5. **Reading.**
   - `threads.get?format=full`. Messages are sorted by `internalDate`. Messages labelled `DRAFT`, `TRASH` or `SPAM` are dropped, so our own draft never becomes the "latest message" and never trips the re-check.
   - Body: the first `text/plain` part, depth-first. If there is none, the first `text/html` part, converted by a small `htmlToText`: drop `script`, `style` and `head`; turn `br`, `p`, `div`, `li` and `tr` into newlines; remove the other tags; decode the named entities `amp lt gt quot apos nbsp` and numeric entities; collapse runs of blank lines.
   - The charset comes from `Content-Type`, through `TextDecoder` (`fatal: false`). An unknown label falls back to UTF-8. Bodies are cut at 20 000 characters.
   - At most 10 MIME levels and 200 parts are read; deeper or more is cut, not an error.
   - Addresses come from a small RFC 5322 list parser: quoted strings, comments, `<…>` and groups. RFC 2047 words in names and subjects are decoded. An entry that does not parse is dropped from the address lists (so it never counts as on the thread).
   - Search: `threads.list?q=<query>&maxResults=<limit>`, then `threads.get?format=metadata&metadataHeaders=From&metadataHeaders=Subject&metadataHeaders=Date` per thread. `truncated` is true when `nextPageToken` is present.
6. **Recordings are hand-written** from the Gmail API reference with made-up ids and `@example.com` addresses (M3b decision 6). The live check proves them, and any mismatch is fixed in the recording and the adapter together before merge.

## Global Constraints

- Every rule from the M4a plan's Global Constraints still holds.
- Scope sets are exactly: read `[calendar.readonly, gmail.readonly]`; write adds `[calendar.events, gmail.compose]`, in that order, only with `DESKHAND_ALLOW_WRITES=1`.
- No Gmail request leaves `googleRequest` unless it is on the decision-2 allowlist. Host stays `www.googleapis.com` and `redirect: "error"` is kept.
- No token, response body, message body or raw MIME appears in a thrown message, `actions.error`, a preview or stderr.
- No live network in tests; `replay-fetch` fails on any `/send` URL.
- Test first. Commits carry no attribution lines.

## Review Focus

1. **A message with no `text/plain` part and malformed HTML** (an unclosed tag, `<script>` with a `>` inside a string). Expected: readable text, no script text, no exception, wrapped as untrusted. Test in Task 2.
2. **A body in `ISO-8859-1` or `windows-1252`, and a part with an unknown charset label.** Expected: decoded correctly, or decoded as UTF-8 with replacement characters, and never thrown. Test in Task 2.
3. **The token predates M4** (calendar scopes only). Expected: calendar tools work; inbox tools answer `AUTH_REQUIRED` `Not signed in to Google. Run: deskhand auth login`; no Gmail request is sent. Test in Task 1.
4. **A thread id in a request path holding `/`, `..`, `%2F` or `?`.** Expected: refused by the allowlist before `fetch`. (The tool's `threadIdSchema` already refuses it; this is the adapter's own guard.) Test in Task 1.
5. **Our draft is the newest message of the thread when apply runs again** (a replay or recovery after the draft was created). Expected: the re-check ignores `DRAFT` messages, so recovery finds the draft and records `applied`, not `STALE_PLAN`. Test in Task 3.

## Review cap (owner rule, applies to this PR)

The same as M4a: one whole-branch review, one red-team round, then at most 2 scoped re-review rounds of the code the fixes touched. The red-team targets are reaching any Gmail endpoint outside the allowlist, MIME header injection, a body or token in errors or previews, and a draft whose stored content differs from the approved diff. Anything still open goes into the PR description under "Open for owner decision". Per-task reviews inside subagent-driven development do not count.
