**M2b decisions (recorded 2026-11-10, reversible):**
- Recovery (provider already holds our idempotency key) runs before the expiry gate, so a write that landed before a crash is finalised `applied` even if the plan has expired since. Gates still fire when nothing was written.
- A provider read error during lookup or re-check leaves the plan `approved` and is retryable (`PROVIDER_ERROR` refusal); only a write failure whose follow-up lookup finds nothing marks it `failed` (best-effort, see above; narrowed to definite rejections in M3b fix wave 1).
- Typed confirmation is trimmed and case-insensitive for ASCII only (`a-z` uppercased; no Unicode case mapping, so `ß`/`ſ` never fold into `S`).
- `deskhand approve` refuses a hash-consistent stored plan of unknown kind or invalid shape with `INTERNAL` before the prompt (check 5b, final review 2026-11-10).
- `hooks.beforeCommit` on `AppContext` is a test seam in production code, used only by the crash-retry test.
- The red-team sandbox (`scripts/redteam-sandbox.mjs`) builds its states through built `dist/` modules (`createPlan`, `rejectAction`, direct SQL for approved/expired/failed/tampered), never from `tests/`. It runs on a fixed fixture clock so its output is reproducible. `cliCommand` is an argv array. A faked-TTY approval is the documented limit (SECURITY.md), not a blocker.
- **For M3: select the provider explicitly.** In M2 the fixture provider is always wired; `DESKHAND_FIXTURE` only loads a world (unset = empty in-memory world, real clock). M3 must choose the provider by explicit configuration, and `action_apply` must refuse when no real provider is configured; otherwise `applied` could be recorded for a write into an in-memory world that dies with the process. **Closed in M3a** (see "Closed in M3a" below).
- **For M3:** Google adapter errors must not carry tokens or response bodies into `actions.error` or event previews (`redactInput` on a bare string only truncates; it does not scrub secrets). `createEvent` with an existing key must return the existing event; a `409` on insert with our key means already created.

**For M3 (recorded 2026-11-10, owner TTY check):** the `deskhand approve` diff shows times in UTC (for example `2026-11-12T10:00:00.000Z`). Once calendar tools land it must show the user's **local time zone, with the zone name** (for example `11:00 CET, Europe/Berlin`), computed from the event's own zone or the user's configured zone, with UTC kept as a secondary detail. Approving a meeting at the wrong hour because the diff was in UTC is a real failure mode. The plan JSON and its hash stay in UTC; only the rendering changes (`renderDiff` in `src/approval/plan-kinds.ts`). **Closed in M3a** (see "Closed in M3a" below; the zone is the viewer's, not the event's).

**M2b shutdown limits (Task 6, 2026-11-10):**
- **The stdin-close drain is capped at 10 s by default.** A real Google write in M3 that is still running at the cap is cut off (exit 1). The re-check and the idempotency key make the retry safe: the recovery gate finds the event and records it as `applied`. **For M3: revisit the cap** against real Google write latency (raise it, or make it configurable) before the Google adapter ships. **Closed in M3a:** default 30 s, configurable (see "Closed in M3a" below).
- **SIGINT/SIGTERM keep Node's default immediate exit** (M1 behaviour). A SIGTERM mid-apply can leave a provider write without its `applied` row; recovery handles it on the next `action_apply`.
- **Exit after a failed stdout flush reports the original code.** If stdout never drains (the client is alive but not reading), the 2 s fallback exits with the drain's code, not 1. A client that closed stdout (EPIPE and similar) counts as gone: no log, exit 0.

**Closed in M3a (2026-11-12; decision numbers refer to `docs/superpowers/plans/2026-11-11-m3a-calendar-fixture.md`):**
- **Provider selection (decisions 1, 2; ADR 0008).** `DESKHAND_PROVIDER` chooses the provider (`fixture` now, `google` in M3b). Unset means no provider: the server starts, calendar tools and `action_apply` refuse with `PROVIDER_NOT_CONFIGURED` (apply gate 1b, after the writes flag). `DESKHAND_FIXTURE` without `DESKHAND_PROVIDER=fixture` is a startup error. Ledger schema v3.
- **Local-time diff (decision 5).** The `when:` line is in the viewer's zone (`DESKHAND_TIMEZONE`, else the system zone), never a zone chosen by the agent. `event.timeZone` stays in the plan (hashed) and gets its own `event zone:` line when it differs. The `utc:` line is always shown. `calendar_propose_event` always stores `event.timeZone` (the `time_zone` input, else `Config.timeZone`). The system-zone fallback of `Config.timeZone` must itself be an IANA name: when Node reports something else (for example `EST5EDT` or `+00:00` for some `TZ` values) startup fails and says to set `DESKHAND_TIMEZONE`.
- **`calendar_id` is restricted (whole-branch review, 2026-11-12).** Tool input accepts 1 to 256 printable ASCII characters with no whitespace. The review showed that a `calendar_id` with newlines forged `0 attendees` / `no attendee notifications` lines in `deskhand pending` and `deskhand approve`. Fixed three ways: the input is refused, the `calendar:` diff line is flattened, and `renderDiff` strips line breaks from every line of every plan kind. The stored-plan schema still accepts any non-empty `calendarId` (a stored plan cannot be re-validated away), which is why the rendering is the real guard.
- **Drain cap (decision 7).** Default raised from 10 s to 30 s; `DESKHAND_SHUTDOWN_TIMEOUT_MS` accepts an integer from 1000 to 120000, anything else is a startup error. A write cut off at the cap is still finalised by the recovery gate on the next `action_apply`.
- **`calendar_find_slots` filters Tempo's suggestions by free/busy (decision 3).** Tempo is asked for 10 candidates; the ones that overlap a busy block are dropped. If all are busy the result is `none` with a note; the tool does not search further.
- **The caller's own rules (decision 4)** come from `rules.json` in the config dir (`DESKHAND_RULES` overrides the path) or the `own_rules` input. Rule sets are not carried in the fixture world.
- **A busy slot is refused at plan time (decision 6)** with `INVALID_INPUT`; no plan row, no new error code.
- **The diff lists every attendee (decision 8),** one line per address after the count.
- **Display equals write (second diff review, 2026-11-12; changes Task 7 of the M3a plan).** The plan said a title with ANSI codes is "stored verbatim" and printed stripped. The review showed why that is unsafe: the sanitiser removed whole escape sequences, so an unterminated `ESC ]` hid the rest of the title from the approver while the full title was written. Now a title must be one line of visible text or the call is `INVALID_INPUT`; title, calendar id and attendees are printed verbatim; the stored-plan schema enforces the same rules, so a row written around the tool is `(invalid plan)` and cannot be approved or applied; `stripControl` removes hidden characters only and never interprets a sequence (`ESC[31m` prints as `[31m`), which also changes what a `reject` reason with escape codes is stored as. Cost, accepted: an emoji that needs a variation selector or a zero-width joiner is refused in a title, and so are double spaces and leading or trailing spaces (the error message says so).
- **The notification line names the stored value (same review).** `externalOnly` with attendees now reads `will email the attendees outside your organisation, up to <n> (sendUpdates=externalOnly)` (it used to claim all `<n>` are emailed), and `all` / `externalOnly` with no attendees reads `no attendee notifications (sendUpdates=<value>, no attendees)` (it used to say `sendUpdates=none`). The two owner-approved lines are unchanged for their own cases.
- **Known and left as is (same review, Minor):** duplicate attendee addresses are counted and listed separately (nothing is hidden; a provider would dedupe); right-to-left letters reorder inside the title line. (A long title or address wrapping on a narrow terminal was on this list; the third review fixed it, next item.)
- **The CLI wraps long diff lines itself (third diff review, 2026-11-14).** `pending` and `approve` lay every diff line and header out to the terminal width (`process.stdout.columns` on a TTY, else 80, never below 20). A row that continues the line above starts with `    | `, so text that a terminal would have wrapped can never start a row and pass for a field. Widths are over-counted (any non-ASCII character counts two columns) so the terminal never wraps a row itself; a row breaks after its last double space, else its last space, else between characters. Lines that fit (the owner-checked diff) are unchanged. On a terminal narrower than 20 columns the terminal wraps the rows again.
- **Wrapping hardened (fourth diff review, 2026-11-14, scoped to the wrapping code).** Every row now fits for any text: carried text is checked to fit on the next row, a single character too wide for a row is split into its code points, and a leading indent is never a break point. Titles also refuse a character built from more than 8 code points (runs made to be one unbreakable character, such as 50 Hangul leading jamo) and a title starting with a combining mark or other extender (it joined the space after `create event:`). The approve footer (`plan hash`, `expires`) is wrapped too. The width comes from stdout when it is a terminal, else from stderr when that is one (`deskhand pending | more`), else 80.
- **A narrower terminal is not trusted (same review).** A terminal re-wraps rows it already printed when it gets narrower (resize, split pane), without the continuation marker. `deskhand approve` watches the width from showing the plan until the answer and refuses (`CONFIRMATION_MISMATCH`, nothing approved) if it shrank; run it again at the new width. `deskhand pending` is a listing and cannot do this: if you resize after it printed, run it again. Getting wider is harmless.
- **Titles refuse blank-rendering and stacked characters (same review).** Unassigned code points and noncharacters (`\p{Cn}`), and characters designed to render blank (U+303F, U+A8F9, U+13441, U+13442, U+16FE4, U+1D159) are refused like the other hidden characters, and `stripControl` removes them elsewhere. More than four combining marks on one character is refused (NFD Vietnamese and pointed Hebrew need at most four).
- **`plan_json` must be canonical (same review).** `pending`, `approve` and `action_apply` treat a row whose `plan_json` is not exactly the canonical form of itself (for example duplicate keys, which `JSON.parse` and SQLite `json_extract` read differently) as an invalid plan. The stored-plan schema now also requires `start` / `end` in the stored form (`YYYY-MM-DDTHH:mm:ss.sssZ`), attendees to be email addresses, and `timeZone` at most 64 characters, matching the tool input.
- **Left as is from the third review (Minor):** the `when:` and `event zone:` lines show minutes only, so an event starting at `10:00:59.999Z` reads `10:00` there (the `utc:` line is exact); time zone names are stored as typed (`EUROPE/BERLIN`, `SystemV/EST5`), already a carry-over to canonicalise first in M3b; a group address counts as one attendee in `will email <n> attendees`.
- **Singular count (owner request, 2026-11-14).** One attendee reads `1 attendee` and `will email 1 attendee`; every other count, including 0, keeps `attendees`.
- **All-day events carry dates (decision 9).** `EventRef.allDay`; `start`/`end` are `YYYY-MM-DD` with `end` exclusive. The fixture format gained the optional event key `all_day` **without a version bump** (`fixture_version` stays 1: the key is additive and nothing outside this repo reads the format yet). In the fixture an all-day event does not count as busy. Plans still create timed events only.
- **Migration 3 adds two error codes (decision 10):** `PROVIDER_NOT_CONFIGURED` and `NOT_FOUND`. `NOT_FOUND` is reserved for M4 (a thread, message or event id that does not exist at the provider) and is emitted by nothing in M3.

**For M3b (recorded 2026-11-12, from the M3a whole-branch review; both are in the M3b plan as carry-overs to do first):**
- **`calendar_find_slots` must give a different note when Tempo returns no candidates.** Today a request Tempo cannot place at all (for example a counterparty with no working hours, or `end` before `start`) comes back as `decision: "none"`, `busy_dropped: 0` and the note `All suggested slots are busy in calendar <id>.`, although nothing was busy. The note must say that no slot fits the rules, and keep the "busy" wording for the case where candidates existed and every one was dropped. `docs/tools-contract.md` changes with it.
- **Time zones are canonicalised before being stored or sent to Google.** `isIanaTimeZone` accepts `europe/berlin`; it is stored verbatim in the hashed plan, shown with a redundant `event zone:` line (the comparison with the viewer zone is a string compare) and would be sent to Google in that spelling. Every accepted zone (`time_zone` inputs, `DESKHAND_TIMEZONE`, the system zone, `event.timeZone`) must be turned into its canonical spelling (`europe/berlin` becomes `Europe/Berlin`) at the point it is accepted, so the plan, its hash and the Google request all carry the canonical name. Open point for the implementation: `Intl` also resolves aliases (for example `Asia/Calcutta`), and the result can differ between ICU versions, so the rule must give the same string on Node 24.15 and 26 for the same input (the CI matrix is the check).

**Closed 2026-11-14 (C2, `fix: canonicalise time zone names where they are accepted`).** `canonicalTimeZone(tz)` in `src/util/local-time.ts` returns the canonical spelling or null (when `isIanaTimeZone` is false) and is applied to the `time_zone` inputs of `calendar_propose_event` and `calendar_find_slots`, `DESKHAND_TIMEZONE` and the system zone, so `event.timeZone` in a new plan is canonical and its hash covers that name. A stored plan with a non-canonical zone stays valid; the diff compares canonical forms. Alias open point, measured on Node 24.22 (ICU 78.3, tz 2026e): `resolvedOptions().timeZone` maps `Asia/Kolkata` to `Asia/Calcutta`, `US/Pacific` to `America/Los_Angeles`, `Etc/UTC` to `UTC`, and `Intl.supportedValuesOf("timeZone")` lists `Asia/Calcutta` but not `Asia/Kolkata` or `UTC`; other ICU versions answer differently, so nothing may depend on either. Resolution (fix round 1, `fix: canonicalise time zones from a pinned name list`): `src/util/tz-names.ts` holds every name of IANA tzdata release **2026e** (all `Zone` names plus all `Link` names from the region files and `backward`, 597 names, generated from the official `tzdata2026e.tar.gz` at data.iana.org, excluding `backzone` and `factory`; the release matches the local ICU tz version). `canonicalTimeZone` does a case-insensitive exact lookup in that list and returns the list's spelling (`etc/utc` is `Etc/UTC`, `america/knox_in` is `America/Knox_IN`, `Asia/kolkata` is `Asia/Kolkata`); `utc` in any case is `UTC`. `Intl` only checks that the runtime accepts the zone (`isIanaTimeZone`); offsets and POSIX names such as `EST5EDT` stay null. Aliases keep their own name and are never resolved. A zone the runtime accepts but the 2026e list lacks (one added later) is returned as typed. The result depends only on the input and the pinned list, so it is identical on Node 24.15 and 26. Moving the pin means regenerating the list from the new release.

**M4a decisions (owner-approved 2026-11-17; numbers refer to `docs/superpowers/plans/2026-11-17-m4a-inbox-fixture.md`; reversible unless noted):**
- **Decision 5, new recipients are flagged, not refused.** `observed.onThread` is computed from the provider (From, Reply-To, To, Cc of each non-draft message plus the owner, case-insensitive, address rule applied) and hashed. Anyone not in it gets `(new: not on this thread)` and a count in the `new recipients:` line. Caveat: someone who is Cc'd on any message counts as "on the thread", even if an earlier sender added them (SECURITY.md).
- **Decision 6, default recipients.** Without `to`: the latest non-owner message's Reply-To, else From; `reply_all` adds its To and Cc minus the owner. All messages from the owner: the latest message's To. With `to`: `cc` and `bcc` default to `[]`.

A draft the user deleted after a crashed apply is created again on retry (it is a draft, never sent). Whether Gmail keeps the header is confirmed by M4b's live check, with a fallback recorded there.

No scope is needed in M4a.
- **R1 (controller ruling).** `approve` on a draft whose present body does not match `bodyChars` / `bodySha256` refuses `PLAN_MODIFIED` (checked before the schema's `INTERNAL`), the same as apply. The red-team sandbox's D2 (body edited in `plan_json`, `plan_hash` kept) shows it.

- **R3 (controller ruling, Task 6 review).** `subject` is a `BODY_KEY` (amends decision 11), so no preview or `input_json` holds a subject in clear. Switching later changes two constants and needs a re-login.

- **Recordings are hand-written (decision 6)** from the API reference with made-up ids and no personal data; the owner's live check is what proves they match reality. A recording's file name must not match the `.gitignore` secret patterns (`token*.json`, `client_secret*.json`, `credentials*.json`).

**M3b fix wave 1 (red-team round 1 and final review, recorded 2026-11-14; controller rulings):**
- **Ambiguous write failures stay retryable (supersedes the M2b best-effort entry above for these cases).** When `createEvent` fails with a timeout, a network error, HTTP `429` or any `5xx` (`ProviderError.retryable`) and the follow-up lookup finds nothing, apply refuses `PROVIDER_ERROR` and the plan stays `approved`. The write may still land; the fixed event id makes the retry safe (it is recovered, or the insert answers `409`). Only a definite rejection with nothing found marks `failed`. A token refresh that fails before the request is sent is retryable too (nothing was sent). An error that is not a `ProviderError` (unreachable from our adapters) stays definite. Residual risk now: a write that lands after the refusal sits behind an `approved` plan until someone applies again; that apply finds it in the recovery lookup (gate 6 runs before expiry, so this works after `expires_at` too) and records it `applied`. Nothing records it automatically.
- **An event under our id must be the approved one.** Recovery, both re-lookups and the event `createEvent` returns (Google `409` path, a concurrent apply) are accepted only when id, title, start and end instants and the attendee set (case-insensitive) match the plan; the calendar is fixed by where it is looked up. A mismatch is `STALE_PLAN`, `failed`, fixed phrase, never re-written. *Superseded by Ruling 13 (fix wave 2): `organizer.self` is now checked; see "The organiser must be you" below.* `creator.self` is not checked (a delegate with write access, see SECURITY.md).
- **The calendar owner in `attendees` (Ruling 13, replaces Ruling 12's "drop and forget").** Google adds the calendar owner to `attendees` with `self: true` (usually `organizer: true`) on events that have attendees, in insert, get and list responses. `mapEvent` leaves that attendee out of `attendees` (what the read tools show) but keeps its address as `ownerEmail`; the plan match accepts the attendee set without the owner (Google added them) or with the owner (the plan invited them explicitly), and nothing else. **To be confirmed by the owner's live check** (the recordings are hand-written): that Google marks the owner `self: true` and adds nobody else.
- **The organiser must be you (Ruling 13).** A found event matches only with `organizerSelf` (Google `organizer.self === true`; requested as `organizer(self)` in the list mask, present in full get/insert responses). This closes the foreign-invite case (RT1-1(a), reopened by Ruling 12 as RT2-2): an invite under our id from another organiser is `STALE_PLAN` "differs" even when every visible field matches. The fixture marks its own writes and (fix wave 3) its world events `organizerSelf: true`. To be confirmed by the owner's live check (an event you create shows `organizer.self: true` in your calendar's copy).
- **Recurring events never match** a single-event plan (`recurrence` or `recurringEventId` present: `recurring: true`).
- **A failed re-check after an earlier ambiguous write is not terminal (Ruling 14).** Detected from the action's own ledger rows (an `apply_refused` row, `PROVIDER_ERROR` or `AUTH_REQUIRED`, whose note starts with the fixed prefix `Provider write failed: `), so it survives restarts. Fix wave 3: every ambiguous attempt writes that row, also when the lookup after it fails (note `Provider write failed: <write error>; the lookup after it failed: <lookup error>`). Not covered: a write cut off by the shutdown drain cap or a kill after the POST was sent writes no row at all; recording an attempt before the write needs a contract decision (owner). Cost: if the slot is really taken by someone else after such an attempt, the plan keeps refusing (status `approved`) until it expires, instead of failing at once.
- **Fixture world events are yours by default (fix wave 3).** World events map to `organizerSelf: true` unless the event has the additive key `organizer_self: false` (a foreign invite); no `fixture_version` bump. This keeps the documented crash simulation (a world event under the idempotency key) recovering as `applied`.
- **An unreadable `2xx` insert body is retryable**: Google created the event; the follow-up lookup, or the retry's recovery, decides.
- **A deleted event is not re-created.** `CalendarProvider.lookupEvent` reports `cancelled` separately from `absent` (getEvent still returns null for both); a cancelled event under our id is `STALE_PLAN`, `failed`, "an event with this action's id was created and later deleted", with no POST. The fixture provider models it with the `cancelEvent` test seam (no fixture-format change).
- **Error codes for the new failures.** A differing or deleted event under our key uses `STALE_PLAN` (the world changed since approval), also on the `409` path that used `PROVIDER_ERROR` before. Value sets unchanged.
- **Login keeps the read scope only.** `include_granted_scopes=true` is sent only by `deskhand auth upgrade` (overrides plan Task 2's parameter list; CLAUDE.md's minimum-scope rule binds), and `runLoopbackLogin` stores only the requested scopes that were granted, so a plain `login` never stores `calendar.events` even if Google reports an earlier grant. To drop an earlier write grant at Google itself, revoke the app at <https://myaccount.google.com/permissions>.
- **Token refresh vs a concurrent login/upgrade.** Before writing a refreshed access token, `token.json` is read again; if its `refresh_token` or `obtained_at` changed (another process signed in), the file is kept and its token used. No lockfile: a second refresh racing a refresh in another process can still overwrite an access token with an equally valid one.
- **Client file missing at refresh** is `AUTH_REQUIRED` "The Google OAuth client file is missing or unreadable. See docs/google-oauth-setup.md" (not "Not signed in").
- **`cli:auth` usage rows are real.** `runCli` no longer rejects bad `auth` arguments itself; `authCommand` writes the documented row (subcommand null, `INVALID_INPUT`) and exits 2.

**M3b red-team review closed at round 18 (2026-11-16). Open follow-ups, not fixed in M3b:**
- **`token.json` temp file is not created exclusively.** `writeToken` writes `token.json.<pid>.<ms>.tmp` with `writeFileSync(..., { mode: 0o600 })` and renames it over `token.json`. It does not pass the `wx` flag, so a file or symlink already at that predictable temp path would be followed or overwritten instead of failing. Exploiting it needs a process running as the same user with write access to the config dir (mode `0700` on POSIX), which can already read `token.json`. Follow-up: open the temp file with `flag: "wx"` and retry with a fresh name on `EEXIST`.
- **A refresh ignores the scopes Google returns.** `refreshAccessToken` keeps the stored `scopes` and does not read the `scope` field of the refresh response, so `token.json` can still list `calendar.events` after the grant was narrowed at Google. This fails safe: Google rejects the write (`403 insufficientPermissions` becomes `AUTH_REQUIRED`) and scopes can never widen through a refresh. Follow-up: when the response has `scope`, store the intersection of the stored and the returned scopes.
- **`src/ledger/redact.ts` may be simplified later (not changed now).** `scrubSecrets` was hardened across rounds 4-16. `redact.ts` was 81 lines on `main`, 143 after round 7, and peaked at 222 lines after round 16 (209 at round 11, then 150 when round 12 replaced in-place rewriting with all-or-nothing). `tests/ledger.redact.test.ts` grew from 158 to 1087 lines over the same rounds. The bounded decode-order search (Rulings 19 and 20) is the bulk of it. Once the error text that reaches `scrubSecrets` is narrowed (for example by making provider error messages fixed sentences only), the search could be reduced or removed; the test file is the safety net for that change.
